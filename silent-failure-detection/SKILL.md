# 静默失效检测（Silent Failure）

## 核心命题
**「有返回」不等于「工作正常」。** 最危险的缺陷不是报错，而是**返回 200 + 空结果**：
- 检索索引分词配置错 → 查不到东西，但不报错
- 检测规则写错字段名 → 永远不触发，看起来"零告警=很安全"
- 备份任务退出码 0 → 实际没传上去
- 监控探针超时被吞 → 面板全绿

## 通用四步法
1. **构造真值**：用最笨但可靠的方式（全表 LIKE / 手工数 / 逐条比对）算出"应该命中多少"
2. **对照召回**：目标系统在同样输入下命中多少 → 召回率 = 命中 / 真值
3. **解释缺口**：缺失部分是"正常过滤"还是"解析/分词/规则失效"
4. **固化基线**：把真值与实测写进测试，回归时自动比对

## 实例：SQLite FTS5 中文检索（实测）
| 查询 | LIKE 真值 | unicode61 索引 | bigram 索引 |
|---|---|---|---|
| 备份 | 555 | 81（14.6%） | 556（100%） |
| 注入 | 1858 | 409（22.0%） | 1864（100%） |
| 提权 | 301 | 113（37.5%） | 301（100%） |

根因：`unicode61` 把连续中文当作**一个 token**，子词查询永远匹配不到；且不报错。

## 检查清单（按易漏排序）
- [ ] 检索：用 3 个"应当命中"的短词做真值对照（中文/英文/编号各一）
- [ ] 检测规则：人为制造一次必定触发的事件，看告警是否真的出现
- [ ] 定时任务：检查输出文件 mtime 与内容，而不只看 exit code
- [ ] 监控：给探针注入一次失败（改错目标端口），确认面板变红
- [ ] 数据同步：对比源/目的条数与校验和，而不是"任务成功"

## 反例约束
- 只测"能查到东西"不算验证，必须测"该查到的是否都查到"
- 召回率高不代表精确率高：噪声太多会让分析师忽略告警（同样致命）

## 交付口径
报告里写「召回 X% / 真值 N / 抽样方法」，不要写「检索功能正常」。
